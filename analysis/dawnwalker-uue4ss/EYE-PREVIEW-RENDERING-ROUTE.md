## Chosen investigation

Use the real game's doll meshes/materials in a native scene capture. The Electron canvas receives newly rendered frames from that native preview. Horizontal interaction must move only a separately owned preview camera or doll hierarchy, never the player actor or player camera. Determine capture/mesh attachment relationships before selecting the actual transform receiver: rotating a shared root that also rotates its capture may produce no visible rotation.

The first probe observes an existing inventory doll after the coordinator opens the normal inventory screen. It never creates or destroys that object and does not call the inventory widget's lifecycle functions. Reusing the normal screen's singleton target for editing is not yet authorized by technical evidence; a separately owned preview or a fully restored lease must be established first.

The probe reads bounded candidate and material-reference lists; records target ownership, independent transforms, target size/format/gamma, main-view flags, capture actor/component lists and doll lighting; then verifies relevant ownership and mesh/material/target topology again. It rejects stale player/world/form identities and separately records wolf form. Optional unsupported getters remain explicit failures. `preview_verified`, `gameplay_verified`, and `mutation_authorized` remain false for every result.

## Shared viewer interface

The [UI contract draft](../../qa/eye-appearance/ui-integration-contract-draft.md) owns the final shared schema. The native descriptor must identify the preview and target generation, attach a bounded capture size, and define validated zoom bounds. Camera commands use `yawDegrees` in [-69, 69] and framing `head-and-shoulders` or `eyes-close-up`; 0 degrees is the calibrated front. Safe close-up bounds require actual head/eye framing and near-plane observations, not guessed distances.

Each frame must correspond to the same session, world, pawn, appearance/material generation and form as the eye controller, including separate wolf state. It needs a monotonically increasing sequence, capture time, view revision and eye-settings revision. A stale/reordered frame cannot establish current preview or in-game success. Mouse capture lasts only for the active preview gesture. Controls and code must not imply a working native renderer until real frames and control receipts arrive.

Frame transport is an unresolved engineering gate. Epic's [UE 5.5 scene capture documentation](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/Components/USceneCaptureComponent2D?application_version=5.5) describes capture output to a render target and main-view-dependent options. Its [UE 5.5 rendering library documentation](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/Kismet/UKismetRenderingLibrary?application_version=5.5) identifies synchronous target reads as expensive. A bounded individual frame can establish content, but repeated synchronous pixel reads or PNG exports cannot be assumed to provide smooth interaction. An asynchronous transfer requires an actual compatible native integration and measurement before adoption.
